Premortem Report

Codex Ratchet Sim Plan

Premise: it is six months from now. The sim plan failed. The failure was not lack of effort, agents, or tests. It was the loss of a hard admission boundary between artifacts that exist and evidence that is allowed to move a stage.

Most Likely Failure

Parallel discovery outruns serial truth admission. Full Wizard produces many probes, receipts, and drafts, but the controller accepts too much because work looks bounded rather than because every exact claim survived runner, manifest, ledger, and demotion checks.

Most Dangerous Failure

Stage gates become prose. Caveats such as "pre-lego only" or "narrow receipt" appear in files while ledger verbs quietly turn micro evidence into coupling, lego, bridge, or axis readiness.

Hidden Assumption

The plan assumes honest receipts naturally constrain later decisions. They do not unless blocker, demotion, and scope findings mechanically change queue, ledger, result, and stage-gate state.

Revised Plan

Add an admission ledger separate from discovery. Every proposed row must resolve to one of accepted, blocked, demoted, deferred, or superseded before queue mutation. Ledger language must be generated from result scope, not synthesis prose.

This Week

Implement a receipt-to-ledger reconciliation check for one row type, starting with tool integrations. Fail if a DONE row claims more than the result JSON, if prior receipts are unnamed, or if demotion conditions are non-operational.

Failure Cards

Wizard Theater

Severity: HighLikelihood: High

Wizard lanes name blockers, thin negatives, and bad demotion conditions, but final synthesis still moves the queue because the report looks complete. Receipts accumulate without any hard rule that turns findings into blocked or demoted state.

Underlying assumption

Honest plural receipts will automatically constrain stage decisions.

Early warnings
  • Receipts contain blockers but queue rows still advance.
  • Final reports cite many voices, but no ledgers or stage-gate files change state.

Parallel Scope Expansion

Severity: HighLikelihood: High

Full Wizard spawns lanes for every adjacent surface. Each agent writes plausible drafts, but accepted result JSONs lag. Queue files gain rows before exact micro receipts, negative tests, demotion conditions, and ledger loopback are complete.

Underlying assumption

Bounded parallel agents will compress work instead of expanding unfinished frontier.

Early warnings
  • More new probes or queue rows appear than accepted classified receipts.
  • Reports say "scouted" or "ready" more often than accepted, demoted, or blocked.

Runner-Ledger Drift

Severity: CriticalLikelihood: High

A row is DONE and a result JSON exists, but ledger wording generalizes a tiny claim into integration readiness. Stale audits and manifests then become authority, leaving future workers unable to tell what was cleared.

Underlying assumption

Result JSONs and DONE rows will naturally keep the ledger truthful.

Early warnings
  • A DONE row has broader ledger wording than the result JSON proves.
  • Audit artifacts reference old schema fields or stale integration status.

Prose Stage Gates

Severity: CriticalLikelihood: Medium

Workers include the right caveats, then cite the same narrow receipt as if it supports coupling, lego, bridge, or axis work. The repo gets two truths: result JSONs prove narrow functions, while ledgers narrate broader readiness.

Underlying assumption

Workers treat caveats as constraints; in practice they may treat caveats as permission.

Early warnings
  • Ledger verbs say supports, suggests, or unblocks without exact runner evidence.
  • Audits ask for wording changes instead of demotion, deletion, or queue rollback.

Low-Value Micros

Severity: HighLikelihood: Medium

The repo fills with correct micro probes that prove a library call returns something plausible. They do not unblock graph/proof integration, preserve invariants across tool boundaries, or move meaningful lego targets.

Underlying assumption

Enough correctly structured micro receipts will naturally compose into research progress.

Early warnings
  • New micros cannot name a downstream lego target, invariant, or queue blocker.
  • Standalone tool manifests turn green while integration ledgers stay red.

Semantic Dependency Drift

Severity: HighLikelihood: Medium

Imports still work and tests still pass after dependency changes, but optional backends, graph label behavior, method signatures, or wrappers change the exact semantic surface that the ledger claims was proven.

Underlying assumption

A receipt remains valid as long as the test runs and the tool name is unchanged.

Early warnings
  • Clean reruns produce changed warnings, backend paths, or optional-import behavior.
  • Result JSON lacks versions, platform details, import path evidence, or semantic drift demotion gates.

Operational Attribution Collapse

Severity: CriticalLikelihood: Medium

Stale helpers, long-tail agents, generated artifacts, and mixed Git staging make it impossible to attribute receipts to the exact run that produced them. Evidence exists, but provenance is no longer trustworthy.

Underlying assumption

Receipts, queues, helpers, agents, artifacts, and Git state remain naturally attributable to the exact run.

Early warnings
  • Workers report conflicting status for the same row or result path.
  • Staging plans mix source, generated results, runtime state, ledgers, and cleanup files.

Pre-Launch Checklist

  • For every queued integration row, require exact prior receipt paths, result scope, and an executable demotion condition before runner admission.
  • After runner DONE, run a reconciliation check that compares queue row, result JSON, manifest/depth, ledger text, and stage-gate state.
  • Reject ledger verbs that widen result scope: supports, suggests, enables, validates, proves, or unblocks require a matching higher-stage result.
  • Require each micro to name the downstream queue blocker or lego-shaped invariant it is meant to unblock; otherwise classify it as exploratory.
  • Before staging, enforce clean process state: no active runner, no stale helper MCPs, no live worker edits, and separate source versus generated-evidence commits.
