## Premortem Report

### The Most Likely Failure

Parallel discovery outruns serial truth admission.

The repo already has strong pressure toward wide worker fanout, many independent tool surfaces, child audits, and quick reroutes around slow lanes. That is good for discovery, but it creates the most probable failure mode: artifacts multiply faster than the controller can classify them as accepted, demoted, blocked, deferred, or superseded. The first symptom will be more new probes, drafts, rows, and "ready" language than runner-DONE receipts with tight ledger loopback.

### The Most Dangerous Failure

Stage gates become prose.

The most damaging failure is not that an individual sim fails. It is that caveats become a laundering mechanism. A ledger row says "narrow micro only," but another sentence says it "supports" integration or "unblocks" a lego. Future agents cite the broader sentence, not the caveat. That would corrupt the repo's truth surface because the failure would look disciplined while silently advancing forbidden claims.

### The Hidden Assumption

The plan assumes that honest receipts, careful wording, and split commits will naturally preserve truth.

They help, but they are not sufficient. Receipt findings only matter if they mechanically constrain queue mutation, ledger text, result classification, and stage-gate state. Otherwise, Full Wizard can produce true observations that are ignored.

### The Revised Plan

1. Add a receipt admission table for every live work item.

   Required statuses: `discovered`, `authored`, `runner_done`, `accepted`, `demoted`, `blocked`, `deferred`, `superseded`. A queue row cannot be added or marked DONE without the row moving through this table. This can start as a small Markdown or JSON file covering only second-wave tool integrations.

2. Make ledger loopback generated from scope facts, not synthesis prose.

   Each ledger update should include fields for exact tool/API surface, result JSON path, prior receipt paths, positive/negative/boundary fixture, demotion condition, and explicit non-claims. Any broader verb requires a higher-stage result path.

3. Add a post-run reconciliation check.

   For each new DONE row, compare queue row, result JSON, `classification`, `tool_manifest`, `tool_integration_depth`, prior receipts, ledger wording, and stage-gate state. Fail if the ledger is broader than the JSON, if prior receipts are unnamed, or if demotion is not executable.

4. Require every micro to name the downstream blocker it unblocks.

   If a micro cannot name a specific queue item, ledger gap, useful lego-shaped invariant, or demotion decision, classify it as exploratory and do not add it to Tier A as load-bearing.

5. Add dependency semantics to receipts.

   Tool micro result JSONs should record package versions, backend/optional-import path, platform where relevant, and a semantic drift demotion condition. A clean rerun with changed backend/warnings should trigger "requires review," not automatic freshness.

6. Preserve process hygiene as a gate, not a cleanup preference.

   Before staging, require no active runner, no stale browser/computer-use helpers, no live workers editing target paths, named-path staging only, and separate source versus generated evidence commits.

### The Pre-Launch Checklist

1. Can this row name exact prior receipt paths and the exact function/API surface being coupled?
2. Does the result JSON prove no more than the ledger claims?
3. Is the demotion condition executable and tied to the claimed function surface?
4. Does the micro name a downstream blocker, invariant, or useful bounded lego target?
5. Are all active workers closed/superseded and is Git staging split by source versus generated evidence?
